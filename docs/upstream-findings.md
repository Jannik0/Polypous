# Upstream findings register

Every problem Polypous found in a dependency it doesn't own: Burn, CubeCL and cubek, and GPU
drivers. For each one it records what Polypous does about it and where it stands upstream.
[status.md §4](status.md#4-known-limitations-and-open-items) describes the user-visible limitations in
detail; this register is the numbered list behind them. How findings are handled is in
[development-workflow.md §8.7](development-workflow.md#87-upstream-burn-and-cubecl-findings).

## Rules

- **IDs** are `M<milestone>-<n>`, numbered in the order the findings were made, and never reused or
  renumbered. One sequence per milestone covers every table below, so an ID is unique. Hand-off
  prompts to the owner's upstream agent refer to these IDs.
- **The lead keeps this file current.** When a worker reports a new finding (under "Decisions" in its
  PR, with a reproduction), the lead adds the row in the same PR or in the next docs PR. When the
  upstream agent reports back, the lead fills in "Upstream". A finding stays in the register after
  it is fixed; its row then says in which version.
- **Re-check after a Burn upgrade** ([ADR-0007](adr/0007-burn-version-pinning.md)): every row with
  "Yes" must be tested again. Switch the workaround off and run the fixtures that showed the problem
  (the negative check of the PR named under "Found in"). If they pass, the workaround can go, in its
  own PR. "Partly" means the workaround is required by the spec anyway, so the re-check is for
  information.
- **Versions:** unless a row says otherwise, Burn 0.22.1, CubeCL 0.11.3 and cubek 0.3.1
  (cubek-matmul, cubek-pool, cubek-random), as pinned by ADR-0007. `flex` is Burn's CPU backend.
  Lavapipe in CI and in cloud sessions is Ubuntu's Mesa 25.2.x. The reference machine runs NVIDIA
  621.14 and Intel 32.0.101.7092 on Windows, and NVIDIA 620.70.06 and Mesa 25.0.7 on Debian.
- **Upstream state:** "Handed off (date)" means the owner gave the finding to the upstream agent on
  that date; "In the … hand-off prompt" means the lead wrote it into a prompt that hasn't been
  confirmed as passed on yet. Upstream links come from the upstream agent's reports (the last one:
  2026-11-23, an update to the full report of 2026-11-21 on every M0 and M1 hand-off); where a row has none, they are still to be added.
  "Merged" means merged to the upstream `main`; Polypous gets it only with the next Burn upgrade.
  The agent's runs were on Windows on the reference machine; it tested nothing on Linux or lavapipe.
- **On GitHub, findings are named by ID only.** This file links upstream, but commits, PRs, issues and
  comments never do: no upstream links or `owner/repo#N` references (CLAUDE.md, "Nothing outside
  Polypous on GitHub"). A PR that updates this file says "M1-13: fix PR open upstream", not the link.

## Observations of the upstream agent

From its reports of 2026-11-21 and 2026-11-23. They aren't Polypous findings and have no ID; none of
them affects Polypous today. They are kept so that they aren't rediscovered. Unless a bullet says
otherwise, they aren't filed.

- **bf16 on Vulkan:** bf16 `conv` returns garbage (`inf`, NaN, 1e38) although the device reports bf16
  as unsupported. The agent commented on another user's issue,
  [burn#6458](https://github.com/tracel-ai/burn/issues/6458#issuecomment-7101672695) (2026-11-23): on
  Burn `main` (c81a904), bf16 conv is still wrong (on NVIDIA only the depthwise and grouped layers,
  on the Intel GPU every layer), and bf16 `matmul` now panics in autotune because every kernel
  declines; it suggests failing early or computing bf16 in f32. Polypous never runs bf16 on a device
  that reports it as unsupported (graph-ir.md §2.2), so this isn't reachable. **On the next Burn
  upgrade,** check that the bf16 `matmul` panic can't be reached on devices that report bf16.
- **f32 and f16 `tanh` on DX12 on the Iris Xe:** f32 `tanh(x)` is NaN for every `|x| >= 89`, f16 from
  about 15, instead of ±1; every other configuration is correct. Filed as
  [cubecl#2272](https://github.com/tracel-ai/cubecl/issues/2272) (open, 2026-11-23; it proposes
  CubeCL's macOS-only `safe_tanh` on every WGSL target, for both signs). Through Burn it also makes
  `gelu_approximate`, `mish` and the `tanh` activation NaN there (relevant to M1-17). Polypous doesn't
  use DX12 or WGSL, and writes its activations from elementary ops.
- **CubeCL's CPU runtime on Windows:** `NaN^0` and `(-1)^-inf` are wrong through the JIT's `pow`, and
  70 bf16 tests fail with `Symbols not found: __truncsfbf2` (on CubeCL `main` too). Polypous uses
  `flex` for the CPU, not CubeCL's CPU runtime.
- **Burn's CI on `main`:** `macos-std-tests` and the documentation build fail on `main`, so they fail on
  every open PR; neither is required to merge. The documentation build has a broken doc link since
  [burn#6536](https://github.com/tracel-ai/burn/pull/6536)
  (`burn-cubecl-fusion/src/optim/reduce/optimization.rs:85`); left to the maintainers, by decision.
